# MP-108 native stalker route check

This check uses the native stalker's movement and physics on a dedicated Windows server. The client recordings and the server log cover the same freshly baked map twice in one server process.

## Prepare the arena

Use the [W1 Level Editor and compiler steps](w0.md#prepare-a-w1-test-arena-on-windows). Build the following into one small DM arena.

| Area | What to put in the map |
| --- | --- |
| Stairs and cover | A wall the bot must go around, stairs with AI nodes on the steps, and a marked goal on the upper floor. Put a walkable lower floor directly below the goal to expose a wrong-floor projection. |
| Door and crowd | A narrow corridor with a solid door a tester can hold closed and release, walk nodes on both sides, and marked goals beyond the doorway and a place to stand as a blocker. Put a bypass in the mesh only if the scenario calls for a detour. |
| Ladder | One exported climbable ladder and two named landing goals several metres from its ends. The upper landing has no walk-grid connection to the foot. Keep the stair goal separate so it cannot act as a walk route to that landing. |
| Unreachable goal | A platform with valid walk nodes and no connection to the bot's region by either walk adjacency or traversal links. |

Use the [MP-105 ladder steps](w0.md#mp-105-ladder-routing-and-traversal) to export the volume and package both link directions. The two directions must use the same baked endpoint IDs in reverse order. Keep the `level.ai`, `level.spawn`, `level.navlinks`, and `w1-fixture.json` from that bake together. Place the MP-005 authoritative stalker fixture on a clear baked node. For a source-level fixture candidate, add **Spawn → stalkers → stalker** (the `stalker` section), enable deathmatch for it, and verify that the dedicated server owns and simulates it and that both clients see it. MP-005 has yet to establish that live fixture. If the stalker is absent or the fixture cannot establish authority, save the logs as a fixture blocker.

Run the normal [W1 navigation startup](w0.md#w1-dedicated-navigation-check) once with this map. Use the `RelWithDebInfo` result with status `w1_navigation_passed`. Save its `report.json` path. Work in the staged runtime it records.

## Start the server and clients

Open a normal PowerShell 7.4 terminal in the Windows checkout. Replace the report path with your successful W1 report. Use an available local UDP port.

```powershell
$W1Report = 'C:path	osuccessfulW1
eport.json'
$Run = Get-Content -LiteralPath $W1Report -Raw | ConvertFrom-Json
$Runtime = Join-Path $Run.workspaceDirectory 'runtime'
$Bin = Join-Path $Run.buildDirectory "bin/$($Run.configuration)"
$Map = $Run.runtime.map
$Port = 54321
$ServerOptions = "server($Map/deathmatch/maxplayers=32/portsv=$Port/public=0/bots=1)"
$ClientOptions = "client(localhost/port=$Port/name=MP108Server)"
"start $ServerOptions $ClientOptions"
Push-Location $Runtime
try {
    New-Item -ItemType Directory -Path 'mp108-server' -ErrorAction Stop | Out-Null
    & (Join-Path $Bin 'xrServerCLI.exe') -overlaypath mp108-server -nosound -mp_route_trace -start $ServerOptions $ClientOptions
} finally {
    Pop-Location
}
```

Keep the server terminal open for console input. If you need a fresh attempt, preserve the old overlay and rename it before launching again. In a second PowerShell terminal in the checkout, set `$W1Report`, `$Run`, `$Runtime`, `$Bin`, and `$Port` to the same values. After the server prints `DM ready`, launch the clients.

Spawn both players, then record one client view while the other player operates the door or blocks the route. Use the MP-005 fixture's server-side stalker ID. ## Record the route suite twice

Mark each observation `pass`, `fail`, or `skip`. Save the first client recording before reloading.

| Key | What to verify in the recording |
| --- | --- |
| `stairs` | The stalker goes around the wall, follows the steps, and reaches the marked upper goal. Its feet stay on the walkable surface. |
| `doorway` | With the door open, the stalker clears the frame and walks beyond the doorway to the goal. |
| `closed_door` | Close the door with the route active. The stalker waits or takes the planned bypass. Open the door and check that the goal becomes reachable if the stalker was waiting. |
| `crowd` | Put the second player in the narrow path. The stalker waits or detours without passing through the blocker, then resumes when the way is clear. |
| `ladder_blocked` | Stand at the upper exit as the stalker climbs. It fails its dismount and releases the ladder. Move clear after the failure. The native trace should record `dismount` followed by `failed` on the first attempt. |
| `ladder_up` | The same stalker retries from the lower landing, climbs, gains ground contact, and walks beyond the upper landing. If it dropped to reachable ground, keep its upper goal active for the retry. |
| `ladder_down` | Give the stalker the lower goal. It climbs down the same ladder, gains ground contact, and walks to the lower mark. |
| `unreachable` | Leave the disconnected platform goal active for ten seconds. The stalker stays on reachable ground. Give it a reachable goal and verify it moves again. |

Give the stalker another route and use `disconnect` in the dedicated console while it is moving. Wait for the closing generation line, then enter the `start` command printed at launch. Wait for the new `DM ready`. Start the second recording and reconnect both clients using `start client(127.0.0.1/port=54321/name=MP108Client1)` and the matching command for client 2. Use your chosen port. Locate the new stalker ID. Verify it starts at the fixture spawn and only begins the test route after the new command. Repeat all eight observations. Save the second recording, then type `quit` in the dedicated console so the engine closes its log.

## Walking controller and recovery

The controller drives the native stalker body through fixed physics steps. It keeps each directed walk edge from the typed plan and consumes one waypoint at a time after grounded arrival. The same blocked-segment policy handles doors and crowds on walking edges and failed climbs on ladder links. When the typed planner can bypass the blockage it uses the alternate route. When the only passage is blocked it retries after the temporary exclusion expires. The current policy waits up to 1.5 seconds for walk progress and retries planning at intervals of at least 500 ms after each failure. A blocked edge or ladder remains excluded for 2.5 seconds.

Run the portable checkpoint first and expect `arena-movement.xml` with `Arena movement checks passed`. For a Windows comparison, use the same freshly baked fixture and scenario first with test-only revision `67ad822a8`, then with the walking controller revision. Run W1 startup for each revision and keep their separate report paths. Record any direct placement or failed movement case on the test-only revision. On the controller revision, confirm ground support and clearance around cover, over stairs, through a doorway, and beyond both ladder landings. Include a crowded corridor where a bypass exists and another pass with the bypass blocked, so the recording shows both replanning and resumption after clearance. Leave a route active when reloading.
