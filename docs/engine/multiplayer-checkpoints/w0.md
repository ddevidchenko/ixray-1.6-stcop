# W0 multiplayer bootstrap

The runner covers MP-010 portable tests, the MP-001 Windows build and gameplay observation, and MP-001/002 runtime startup regressions. The definition fixes the build configuration, targets, cases, and deadlines. [W0 definition](../../../src/test/multiplayer/checkpoints/W0.json)

## Windows

Use PowerShell 7.4 or newer, Git for Windows, CMake 3.26 or newer, and Visual Studio 2022 with the x64 C++ desktop toolchain and Windows SDK. Put `git`, `cmake`, and `ctest` on `PATH`. The engine build also needs access to the repository's package sources. `Portable` and `BaselineBuild` use source already available in the local Git checkout and require no installed game data.

From the repository root, set `$Revision` to the full SHA supplied for W0. The runner fetches that exact commit into a fresh validation checkout and checks its SHA and clean status before building. Use a short writable results root such as `C:\w0` if the ordinary checkout has a deep path.

```powershell
$Revision = '<full W0 candidate SHA>'
pwsh -NoProfile -File scripts/multiplayer/windows/RunCheckpoint.ps1 -Revision $Revision -Mode Portable
pwsh -NoProfile -File scripts/multiplayer/windows/RunCheckpoint.ps1 -Revision $Revision -Mode BaselineBuild
```

- `Portable` builds `TestMultiplayerUnit` on x64 in `RelWithDebInfo`. The ordinary comparison suite must pass and the opt-in inverted assertion must fail with its expected diagnostic. `portable_passed` records both outcomes. Allow a few minutes for a local source transfer, configure, and build.
- `BaselineBuild` configures `Server-x64-Windows` with SQL disabled and builds `xrEngine` and `xrServerCLI` in `RelWithDebInfo`. A cold build can take tens of minutes. The runner records `build_passed` after both targets build.

Each invocation prints a unique `build/test-results/multiplayer/<sha>/<run-id>/report.json` path. Return the report with `logs/` and the two XML reports when present. The report identifies the exact checkout, stage commands, exit codes, and timeouts. Any unexpected result returns a nonzero runner exit and retains the files written so far.

Rerun the same command to create a fresh validation checkout and report. A stage timeout stops its process tree. After a run finishes, keep its report and delete the run's `source` and `portable-build` directories if you need to reclaim space.

## Runtime startup regressions

Run these cases from an interactive PowerShell window on the Windows desktop. Supply a standard CoP game-data installation with the IX-Ray assets and a lowercase DM map identifier. The map can be loose under `gamedata/levels/<map>/` or a map-named `.db`/`.xdb` archive under `mp/`. The runner copies stock assets to its own directory before starting any engine process. Use a short results root with enough space for a fresh game-data copy and a cold engine build per invocation. Allow several minutes for copying and up to an hour for the build.

```powershell
$GameDataRoot = 'C:\Games\IXRay'
$Map = 'mp_atp'
pwsh -NoProfile -File scripts/multiplayer/windows/RunCheckpoint.ps1 -Revision $Revision -Mode BaselineRuntime -RuntimeCase ListenerFailure -GameDataRoot $GameDataRoot -Map $Map -ResultsRoot C:\w0
pwsh -NoProfile -File scripts/multiplayer/windows/RunCheckpoint.ps1 -Revision $Revision -Mode BaselineRuntime -RuntimeCase Join -GameDataRoot $GameDataRoot -Map $Map -ResultsRoot C:\w0
```

- `ListenerFailure` reserves a UDP port and starts the server on it. The captured stdout must contain the bind error followed by the game startup failure, without a DM-ready event. The result is `listener_failure_observed`.
- `Join` starts the dedicated server, then launches two external clients after server readiness. The server must record two distinct ready DM peers from those processes. The engine logs must show app data, logs, saves, screenshots, and downloads under each process's own root. The result is `runtime_smoke_passed`.

Run both revisions from the fixed runner checkout with the same game installation and map. First use the test-only SHA `f103ef3e9` expanded to 40 characters with `git rev-parse f103ef3e9`, then use the full fixed candidate SHA. The test-only `ListenerFailure` case is expected to lack the propagated startup error. The test-only `Join` case is expected to lack the authoritative readiness marker. Report build errors, missing content, crashes, and failed markers with their stage evidence. The runner prints the report path, terminates its own children, and retains stdout, stderr, and any engine logs. Return `report.json` with its `logs/` directory. After preserving the report, the run-owned `source/` and `runtime/` trees can be removed to reclaim space.

## Two-client gameplay observation

Run `Observe` from the same interactive Windows terminal, with `$Revision` set to the candidate that contains this mode. Use the same `$GameDataRoot` and `$Map` as the startup checks.

```powershell
pwsh -NoProfile -File scripts/multiplayer/windows/RunCheckpoint.ps1 -Revision $Revision -Mode BaselineRuntime -RuntimeCase Observe -GameDataRoot $GameDataRoot -Map $Map -ResultsRoot C:\w0
```

`Observe` runs the `Join` checks first and records their result in `runtime.startupPassed`. A fixed-candidate `Observe` run can supply startup evidence and gameplay observations together. Once both clients are ready, the runner keeps the match open for a ten-minute checklist. Follow the prompts for firing, death and scoring, respawn, disconnect, and reconnect. The default game controls use the backtick key for the console and Tab for the scoreboard. Disconnect from the game console and leave the client app open for the displayed reconnect command.

Return to PowerShell after each action. Press `Y` when you saw the expected result, `N` if the action failed, or `S` if you skipped it. Press `Q` to stop the match early and save what you recorded. The runner closes its own processes and collects their logs.

`runtime_observation_passed` requires an explicit `Y` for every action. A failed action returns `runtime_observation_failed`. Skips, an early stop, or the deadline return `runtime_observation_incomplete` when no action failed. Unexpected process exits report a runtime failure. The report includes each decision and its timestamp. Return `report.json` with `logs/` and use the generated `observation-notes.txt` to describe anything the checklist missed.

## macOS portable check

With PowerShell 7.4 or newer, `pwsh -NoProfile -File src/test/multiplayer/checkpoints/TestW0Evidence.ps1` exercises the evidence checks without engine processes. Expect `W0 evidence checks passed.`

```sh
cmake -S src/test/multiplayer/portable -B build/mp-portable -DCMAKE_BUILD_TYPE=Debug
cmake --build build/mp-portable
ctest --test-dir build/mp-portable -N
ctest --test-dir build/mp-portable --output-on-failure --no-tests=error
```

To check failure propagation, use a separate build so ordinary test runs stay green.

```sh
cmake -S src/test/multiplayer/portable -B build/mp-portable-proof -DCMAKE_BUILD_TYPE=Release -DIXRAY_MULTIPLAYER_VERIFY_TEST_FAILURE=ON
cmake --build build/mp-portable-proof
ctest --test-dir build/mp-portable-proof --output-on-failure --no-tests=error -R '^Multiplayer\.Sequence$'
ctest --test-dir build/mp-portable-proof --output-on-failure --no-tests=error -R '^Multiplayer\.Sequence\.DeliberateFailure$'
```

The last command should fail with `deliberate failure: expected IsSequenceNewer to return false`. On macOS arm64 with Apple Clang 21 and CMake 3.31.10, the ordinary run returned zero and this deliberate failure returned 8.
