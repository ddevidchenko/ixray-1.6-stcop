# W0 Windows multiplayer check

## Before you start

Use your existing Windows build setup and open PowerShell 7.4 or newer from the W0 candidate checkout. Keep `git`, `cmake`, and `ctest` on `PATH`. W0 uses `cmake -B <build-dir> -A x64` and lets CMake select the generator. Use CMake 3.26 or newer with Visual Studio 2022, or CMake 4.2 or newer with Visual Studio 2026. [Project requirements](../../../.github/README.md#requirements), [CMake’s Visual Studio 2026 generator](https://cmake.org/cmake/help/v4.2/generator/Visual%20Studio%2018%202026.html)

For the match, use a Call of Pripyat installation with the IX-Ray assets and an installed DM map. Use the lowercase map name from `gamedata/levels/` or from its matching `.db` or `.xdb` archive in `mp/`. Replace both examples below with your local values.

## Run the two-client check

```powershell
$Runner = '.\scripts\multiplayer\windows\RunCheckpoint.ps1'
$W0 = @{ Revision = (git rev-parse HEAD) }
$Game = @{ GameDataRoot = 'C:\Games\IXRay'; Map = 'mp_atp' }
& $Runner @W0 @Game -Mode BaselineRuntime -RuntimeCase Observe
```

W0 keeps the isolated checkout (`s\`) and CMake build (`b\`) in a short workspace under `<checkout>\build\w0\<id>`. W0 keeps `report.json` and `logs\` under `<checkout>\build\test-results\multiplayer\<sha>\<run-id>`. The report records the workspace and build paths.

If the build fails on path length, keep the failure log and use `-WorkspaceRoot` with a shorter directory path on an existing drive. `-ResultsRoot` controls the report and log location.

The runner builds the exact commit with multiplayer enabled, stages a copy of the game data, and starts a dedicated server and two windowed clients. Allow time for a cold build and asset copy. Once both clients join, follow the terminal’s ten-minute checklist for firing, death and scoring, respawn, disconnect, and reconnect. The default game controls use backtick for the console and Tab for the scoreboard. Leave both client windows open and use the reconnect command printed by the runner.

After each action, return to PowerShell and press `Y` if you observed the expected result, `N` if it failed, or `S` to skip it. Press `Q` to finish early and keep your results. The runner closes its own processes and prints the path to `report.json`. Return that file with `logs/` and any notes you add to `observation-notes.txt`. After the run, you can reclaim space by deleting the directory recorded in `workspaceDirectory`.

`runtime.startupPassed` records the automated join and writable-path checks. `runtime_observation_passed` requires confirmation of every gameplay action. Failed and incomplete observations retain their individual results in the report. The operator reports that W0 passed on Windows. The result bundle is pending attachment.

## Prepare a W1 test arena on Windows

Make a small new map named `w1_arena`. A flat room or patch of ground is enough for this checkpoint. The compiler produces `level.ai`, which is where a stalker can walk, and `alife.spawn`, which contains the matching graph and patrol data. Build both from the same editor scene.

### 1. Set up an editor folder and a game copy

Use the Windows checkout you used for W0. Keep an SDK working folder with `fs.ltx`, `fsfactory.ltx`, `fsgame.ltx`, `gamedata` and `rawdata`. If you have only built the editor from source, set up compatible CoP editor assets first. The CoP editor package provides the editor setup files. Check that the editor opens its object library and that you have one flat, textured static object to use as a floor. The repo's `rawdata` is small. A working CoP SDK object library can supply a floor object. The original archives supply compiled levels and textures. If the object library has no floor, use the [optional conversion steps](#if-you-only-have-compiled-map-files). [IX-Ray release packages](https://github.com/ixray-team/ixray-1.6-stcop/releases)

Make a separate copy of the game-data folder that passed W0. Use that copy for `$GameRoot`. Set both paths below to your actual folders. In PowerShell 7.4 or later, run from your Windows repo checkout. Reuse the executables from your current build if you already have them.

```powershell
$Sdk = 'C:\Games\IXRay-W1-SDK'
$GameRoot = 'C:\Games\IXRay-W1'
$Map = 'w1_arena'
cmake -S . -B build/w1-sdk -A x64 -DIXRAY_EDITORS=ON -DIXRAY_UTILS=ON -DIXRAY_MP=OFF
cmake --build build/w1-sdk --config RelWithDebInfo --parallel --target LevelEditor xrLevelBuilder xrSE_Factory xrCompress
$Tools = (Resolve-Path 'build/w1-sdk/bin/RelWithDebInfo').Path
Start-Process -FilePath (Join-Path $Tools 'LevelEditor.exe') -WorkingDirectory $Sdk
```

### 2. Make the small scene

1. Open **Properties**, then find **Scene**. Set **Build options → Level path** to `w1_arena`, **Map version** to `1.0` and enable **deathmatch** in **Game Type**. Save the scene in the SDK.
2. Add the flat static object from the library or use a flat area from the converted scene. Keep the playable area small, with enough room for two people and a stalker to move. Use a texture that is already present in the game copy. Add an outdoor light and use **Sector → Create Default** if you start with an empty scene.
3. In **Spawn**, add two `$rpoint` objects on clear ground several metres apart. For each, set **Spawn Type** to **Actor Spawn**, **Team** to **0**, and enable **deathmatch** under **Game Type**. These are where the two human players enter.
4. Select the floor. In the **Snap List**, use **Make List From Selected**. Switch to **AI Map**, use the add tool to put one seed on the floor and click **Generate Full**. Check that the grid stays on the walkable surface and connects the spawn area. Put two **ai → graph point** markers on separate reachable cells. Add exactly one ordinary **actor** spawn on a walkable cell. The spawn compiler needs that actor to build the graph. The staging script keeps the compiler spawn file out of the game copy.
5. Save, then choose **Compile → Make → Make All**. Check that `$Sdk\gamedata\levels\w1_arena` contains `build.prj`, `build.aimap`, `level.game`, and `level.spawn`. If either of the last two is missing, check the spawn markers and run **Compile → Make → Make Game** again. If `build.aimap` is missing, check the grid and run **Compile → Make → Make AI-Map (25 bit)**.

### 3. Compile, stage and run

```powershell
Start-Process -FilePath (Join-Path $Tools 'xrLevelBuilder.exe') -ArgumentList '-fsltx fsgame.ltx' -WorkingDirectory $Sdk
```

Select only `w1_arena` in the compiler. Enable the **Lighting Compiler** and click **Run Compiler** to build the playable level and collision. When it finishes, turn the **Lighting Compiler** off and enable the **AI Compiler**. Enable **AI Compiler ai.level**, **Verify**, **AI Compiler all.spawn**, **Auto Register Levels**, and **FreeMP Build**. Leave **Draft AI-Map** off. Click **Run Compiler**. The last two expected files in the level folder are `level.ai` and `alife.spawn`. If the compiler reports no actor or invalid graph points, check that the ordinary actor and both graph points are on the generated grid, then re-export and recompile. Keep the compiler log if it fails.

From the same checkout, stage the completed map and launch the check.

```powershell
$Cooked = @{ EditorRoot = $Sdk; GameDataRoot = $GameRoot; Map = $Map }
$FixtureReport = & .\scripts\multiplayer\windows\PrepareW1Fixture.ps1 @Cooked
$FixtureReport
$Runner = '.\scripts\multiplayer\windows\RunCheckpoint.ps1'
$Game = @{ GameDataRoot = $GameRoot; Map = $Map }
$W0 = @{ Revision = (git rev-parse HEAD) }
& $Runner @W0 @Game -Mode BaselineRuntime -RuntimeCase StalkerNavigation
```

The preparation script checks the required compiled files, two distinct DM spawn positions, and the graph and patrol chunks. It copies the playable map into your game copy and writes `w1-fixture.json` with SHA-256 hashes. It refuses an existing destination map. Keep the editor folder and the game copy separate. The Windows engine checks that the navigation data matches the map.

### If you only have compiled map files

Use this route if you need geometry for the editor. Reuse one small map that passed W0. `mp_atp` is an example. Use the actual lowercase folder name from your game. Unpack locally and keep the files in your scratch workspace. [xrCompress syntax](../../docs/main/en/utilities/compressor.md)

```powershell
$FromMap = 'mp_atp'
$Unpacked = 'C:\Games\IXRay-W1-Unpacked'
$null = New-Item -ItemType Directory -Path $Unpacked -Force
Copy-Item -LiteralPath .\fsgame.ltx -Destination (Join-Path $GameRoot 'w1-unpack.ltx')
Push-Location $GameRoot
try {
    & (Join-Path $Tools 'xrCompress.exe') -unpack w1-unpack.ltx (Join-Path $Unpacked 'gamedata')
} finally {
    Pop-Location
}
Test-Path -LiteralPath (Join-Path $Unpacked "gamedata/levels/$FromMap/level")
```

Expect `True` on the last line. In the converter's folder, use its CoP file-system template `fsconverter_cop.ltx` as `fsconverter.ltx` and set `$sdk_root$` to your SDK working folder. In `converter.ini`, set `$game_data$` and `$game_levels$` under `3870_config` to the extracted `gamedata` and `gamedata\levels`. Keep the trailing backslash in those configuration paths. With the converter's PowerShell terminal in the converter folder, run the read-only check first, then run the conversion if it finds your map. [Converter releases](https://github.com/abramcumner/xray_re-tools/releases), [CoP settings](https://github.com/abramcumner/xray_re-tools/blob/812d93d/etc/converter.ini), [converter command reference](https://github.com/abramcumner/xray_re-tools/blob/master/docs/tools/converter_en.txt)

```powershell
.\converter.exe -ro -level "cop:${FromMap}" -out w1_source -mode le -with_lods
.\converter.exe -level "cop:${FromMap}" -out w1_source -mode le -with_lods
```

Open `w1_source.level` from the SDK's `rawdata\levels`. Check that geometry and textures appear before choosing a small walkable area and continuing at [step 2](#2-make-the-small-scene). Keep `converter.log` if the conversion or import fails. Rebuilding the scene is a compatibility check for your asset revision and SDK. [Navigation pipeline](../multiplayer-navigation-pipeline.md#decompilation-and-the-editors-repository-ownership)

## W1 dedicated navigation check

Use the inputs above, or an existing DM arena with matching, compiler-produced `level.ai` and `alife.spawn`. Keep the same game copy and map for both revisions. Run the comparison below when collecting the test-only and fixed reports.

```powershell
$TestOnly = $W0.Clone()
$TestOnly.Revision = git rev-parse cac3c66a9
& $Runner @TestOnly @Game -Mode BaselineRuntime -RuntimeCase StalkerNavigation
& $Runner @W0 @Game -Mode BaselineRuntime -RuntimeCase StalkerNavigation
```

The fixed candidate should report `w1_navigation_passed` and `runtime.navigationStatus = ready`. The runner supplies the dedicated DM option and starts both clients after server readiness. Allow time for the build and asset copy, then up to two minutes for the dedicated server and three minutes for the client joins. No gameplay input is needed.

A test-only candidate that reaches DM readiness with `runtime.navigationStatus = not_loaded` reproduces the missing graph-only startup. A missing fixture, an old ALife startup failure, a crash, or a timeout is recorded separately. Return the `w1-fixture.json` printed by preparation along with the compiler log and each `report.json` and `logs/` from `build/test-results/multiplayer/<sha>/<run-id>/`. The runner closes its own processes when finished. This check covers dedicated navigation and two human joins. The NPC gameplay scenario follows separately. The preparation script was exercised with synthetic inputs on macOS. The editor bake and Windows runtime steps still need execution.

## Run the portable and peer batch

From the candidate checkout, use the same `$Runner` and `$W0` values as above. The batch needs the Windows CMake and NuGet environment and local UDP loopback access. It uses the existing Windows GNS 1.4.1 and LZO 2.10 packages. Game files and gameplay actions are unnecessary for this batch.

```powershell
& $Runner @W0 -Mode Peers
```

The runner configures the x64 multiplayer build with tests enabled and SQL disabled, then builds `TestMultiplayerUnit`, `TestMultiplayerGns`, and `TestMultiplayerLegacyCompression` in `RelWithDebInfo`. The unit suite, deliberate harness failure, GNS loopback, and native LZO checks run from that build. For MP-021b, `legacy-compression.xml` records the packed checksum and LZO bounds cases. Expect `peers_passed` in `report.json`. For MP-020h, `client-join.xml` records the barrier codec cases and `client-catch-up.xml` records the serialized barrier handoff. For MP-020i, `catch-up-despawn.xml` records the despawn codec and catch-up handoff.

For MP-027a, return `reliable-send-queue.xml` and `gns-reliable-send-pressure.xml`. The first checks deterministic queue limits and deadlines. The second forces native send-buffer pressure on a local UDP connection and verifies that both frames arrive reliably and in order when capacity returns. CTest bounds the pressure case to ten seconds.

For MP-027b, return `snapshot-send-queue.xml` and `gns-snapshot-send-pressure.xml`. The portable case checks capture replacement, packet limits and expiry. The peer case refuses a snapshot packet with a reduced native send buffer, restores capacity and checks that the replacement capture arrives as an unreliable datagram. CTest bounds the peer case to ten seconds.

For MP-027c, return `outgoing-traffic.xml` and `gns-outgoing-traffic-pressure.xml`. The peer test delays loopback receipt to hold reliable bytes outstanding, then checks that control and gameplay still arrive and bulk resumes after acknowledgements. CTest bounds the peer case to twelve seconds. For MP-027d, `baseline-send.xml` checks transfer order, refusal and receiver assembly.

Return the result bundle from `build/test-results/multiplayer/<sha>/<run-id>/`. It includes `report.json`, the per-test XML files, and `logs/`. A missing test, assertion failure, or expired loopback deadline returns a failure and keeps its logs. The same batch can run alongside `Observe` in the next Windows session.

On macOS the standalone peer target fetches the pinned GNS source at configure time. It needs OpenSSL and a matching native Protobuf library and `protoc`. The macOS build was verified with OpenSSL 3 and Protobuf 3.20.3. Set `CMAKE_PREFIX_PATH` if those dependencies live outside your toolchain's default search paths.

```sh
cmake -S src/test/multiplayer/gns -B build/mp-gns -DCMAKE_BUILD_TYPE=Release
cmake --build build/mp-gns --target TestMultiplayerGns
ctest --test-dir build/mp-gns --no-tests=error --output-on-failure
```

The standalone native compression target on macOS uses the system LZO library. Set `CMAKE_PREFIX_PATH` if LZO lives outside the toolchain's default search paths.

```sh
cmake -S src/test/multiplayer/legacy-compression -B build/mp-legacy-compression -DCMAKE_BUILD_TYPE=Release
cmake --build build/mp-legacy-compression --target TestMultiplayerLegacyCompression
ctest --test-dir build/mp-legacy-compression --no-tests=error --output-on-failure
```

On macOS, `pwsh -NoProfile -File src/test/multiplayer/checkpoints/TestW0Evidence.ps1` checks runner decisions without starting the engine.
